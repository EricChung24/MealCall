# MealCall 前端第一版設計

## 目標

建立家庭共用的三餐與冰箱庫存管理前端。煮飯者可自訂餐點名稱、登記預計使用的食材並發布；發布後食材會被保留，避免家庭成員重複安排同一批庫存。

第一版只實作前端互動與假資料，不串接 Supabase、登入、資料庫或推播。

## 使用者與權限

所有資料屬於一個家庭空間，共用一個冰箱庫存。

| 類型 | 能力 |
| --- | --- |
| 查看者 | 查看看板、餐點、庫存與補貨清單。 |
| 煮飯者 | 建立、修改、發布、取消與完成自己負責的餐點。 |
| 管理員 | 管理所有餐點、庫存、成員及權限。 |

介面會保留角色和逐項權限設定的呈現方式；第一版以假資料模擬，不做真正的帳號授權。

## 主要畫面

### 家庭看板

- 顯示今天和未來數天的早餐、午餐、晚餐。
- 每筆餐點顯示：餐期、日期、名稱、煮飯者、使用食材與狀態。
- 顯示冰箱庫存摘要與低於安全庫存的補貨清單。
- 放置「查看全部庫存」按鈕；桌機版放在看板右側，手機版放在上方。

### 建立與編輯餐點

- 選擇日期與餐期（早餐、午餐、晚餐）。
- 煮飯者可自行輸入餐點名稱。
- 可新增食材與預計用量。
- 發布前顯示庫存是否足夠；不足時禁止發布並標明缺少食材。

### 餐點詳情

- 顯示餐點、煮飯者與食材明細。
- 具權限者可修改、取消，或標記為已完成。

### 全部庫存

- 逐項顯示食材名稱、總庫存、已保留量、可用量、安全庫存與補貨狀態。
- 提供「全部／不足／已保留」篩選。

### 成員與權限

- 顯示家庭成員、預設角色及逐項能力開關。
- 第一版僅提供展示與互動假資料。

## 資料模型（前端假資料）

```txt
Household
Member: role, permissions
Ingredient: name, unit, safetyStock
Inventory: ingredientId, quantity
Meal: date, slot, title, cookId, status
MealIngredient: mealId, ingredientId, plannedAmount, reservedAmount, consumedAmount
```

庫存計算：

```txt
可用量 = 總庫存 - 所有已發布餐點的保留量
```

## 餐點狀態與庫存流程

```txt
草稿
  → 已發布：依預計用量保留食材
  → 已完成：將保留量轉為實際消耗，扣除總庫存
  → 已取消：釋放保留量，總庫存不變
```

發布到未來日期是支援的；發布後看板應立即顯示該餐點與保留食材。

## 前端防呆

- 可用庫存不足時不能發布。
- 同日期同餐期已有已發布餐點時，提示使用者編輯或覆蓋既有餐點。
- 已完成餐點預設不可修改食材用量。
- 取消或刪除前需確認。
- 每次狀態變更後立即更新餐點、庫存與補貨清單。

## 驗收情境

1. 發布餐點後，相關食材的保留量增加、可用量減少。
2. 取消已發布餐點後，保留量歸還。
3. 完成餐點後，總庫存依使用量扣除。
4. 庫存不足時，不能發布並顯示缺少項目。
5. 從看板可進入完整庫存頁並使用篩選。

## 後續階段

第二階段以 Supabase 實作家庭資料隔離、登入和實際權限控管，並使用 Vercel 部署。即時同步與推播通知會在資料層完成後再加入。
